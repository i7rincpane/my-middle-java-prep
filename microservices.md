## <a id="retry-p">Дефолтные Retry: межсервисная обработка ошибок и повторы</a>

В распределенных системах кратковременные сетевые сбои или перезагрузка сервисов — это норма. Чтобы не возвращать пользователю ошибку при первом же «чихе» соседнего сервиса, мы внедрили механизм **Backoff Retry**.

#### 1. Стратегия Exponential Backoff
Мы не повторяем запросы мгновенно, чтобы не добить «приунывший» сервис (эффект DDoS).
*   **Backoff**: Время между попытками увеличивается экспоненциально (например, 2с, 4с, 8с).
*   **Jitter**: Добавление случайного фактора в задержку, чтобы распределенные инстансы не стучались в соседний сервис одновременно.

#### 2. Разделение типов ошибок (onStatus)
Критически важно разделять ошибки на те, которые стоит ретраить, и те, которые бесполезны:
*   **422 Unprocessable Entity (Бизнес-ошибка)**: Например, «недостаточно товара». Ретрай не поможет — товар не появится сам собой через 2 секунды. Мы сразу пробрасываем OrderCreationException.
*   **5xx Server Error (Системная ошибка)**: Внешний сервис упал или тормозит. Здесь мы выбрасываем ServiceException, на который настроен фильтр ретрая.

#### 3. Реализация универсального конфига
Мы вынесли настройки ретрая в application.yml, чтобы управлять стабильностью системы без пересборки кода.

```java

@Bean
public Retry retryDefault (RetryDefaultProperty property){

    return Retry.backoff(property.maxAttempts(), Duration.ofSeconds(property.minBackoff()))
            .jitter(property.jitter())
            .filter(ex -> ex instanceof ServiceException)
            .onRetryExhaustedThrow((retryBackoffSpec, retrySignal) -> {
                log.error("Все попытки ({}) исчерпаны", retrySignal.totalRetries());
                return retrySignal.failure();
            });

}


private final Retry retryDefault;

    public Mono<Void> decrease(List<StockUpdateRequest> requests) {
        return productWebClient.post()
                .uri("/api/v1/products/stock/decrease")
                .bodyValue(requests)
                .retrieve()
                // Бизнес ошибка, не ретраим
                .onStatus(httpStatusCode -> httpStatusCode.value() == 422,
                        clientResponse -> clientResponse.bodyToMono(String.class).map(OrderCreationException::new).flatMap(Mono::error))
                // Серверная ошибка, оборачиваем, чтоб включился ретрай
                .onStatus(HttpStatusCode::is5xxServerError,
                        clientResponse -> clientResponse.bodyToMono(String.class).map(ServiceException::new).flatMap(Mono::error))
                .bodyToMono(Void.class)
                .retryWhen(retryDefault)
                .doOnSuccess(v -> log.info("Остатки успешно списаны для {} позиций", requests.size()));

    }
```

#### 4. Сравнение подходов

| Ситуация | Поведение WebClient по умолчанию | Наше решение (onStatus + Retry) |
| :--- | :--- | :--- |
| **Ошибка 500** | Выбрасывает WebClientResponseException | Оборачивает в ServiceException и делает 3 попытки |
| **Ошибка 422** | Выбрасывает WebClientResponseException | Превращает в понятную бизнес-ошибку для клиента |
| **Таймаут/Обрыв** | Цепочка сразу падает | Ретрай пытается восстановить соединение |

#### 5. Топ вопросов на собеседовании:

**В: Почему нельзя делать ретраи на все ошибки подряд?**
**О:** Ретраи на 4xx ошибки (Client Error) бесполезны и создают лишнюю нагрузку. Если клиент прислал невалидные данные, они не станут валидными через секунду. Ретраи нужны только для Idempotent операций и только на ошибки типа 5xx или Timeout.

**В: Что такое "Retry Exhausted"?**
**О:** Это состояние, когда все попытки (например, 3 из 3) были выполнены, но сервис так и не ответил успешно. В этом случае мы пробрасываем финальное исключение в GlobalExceptionHandler.

**В: Как retryWhen сочетается с CircuitBreaker?**
**О:** Ретрай работает на «короткой дистанции» (пытается починить один запрос), а CircuitBreaker — на «длинной» (если много запросов подряд падают, он полностью разрывает связь на время, чтобы дать сервису восстановиться).


## <a id="cb-p">Circuit Breaker: Зачем он нужен на самом деле?</a>

CircuitBreaker нужен для того, чтобы быстро убить запрос, не дожидаясь тайм-аута, и защитить свой сервис от перегрузки. С CircuitBreaker, как предохранитель, чтоб постоянно не долбиться в отвалившийся сервер,
мой сервис пробует несколько раз постучаться, и в какой-то момент больше даже не пробует из за CircuitBreaker, не нагружая сетиой вызов.

### 1. Защита от "Эффекта Домино" (Fail Fast)
Если внешний сервис (например, Product Service) тормозит (отвечает по 30 секунд), без CB твои потоки быстро закончатся, так как они будут висеть в ожидании.
Что делает CB: Как только он видит серию ошибок или задержек, он "размыкает цепь" и мгновенно убивает все последующие запросы, не пытаясь стучаться в сеть. Твой сервис остается "живым" и свободным для других задач.

### 2. Карантин для упавшего сервиса
Если сервис упал под нагрузкой, постоянные попытки достучаться до него (retries) только усугубят ситуацию (DDoS собственного сервиса).
Что делает CB: Он дает упавшему сервису время на "передышку" (Wait Duration), вообще не отправляя туда запросы в течение заданного времени.

### 3. Автоматическое восстановление
Тебе не нужно вручную проверять, поднялся ли соседний сервис.
Что делает CB: Переходит в состояние Half-Open, пропускает пару "пробных" запросов и, если они успешны, сам возвращается в рабочий режим.

### Принцип работы (Состояния)

1. CLOSED (Закрыт): Все хорошо, запросы проходят. CB считает статистику (успехи/ошибки).
2. OPEN (Разомкнут): Процент ошибок превышен. Запросы блокируются мгновенно (CallNotPermittedException). Сервис "отдыхает".
3. HALF-OPEN (Полуоткрыт): Время ожидания вышло. CB пропускает тестовые запросы, чтобы проверить состояние соседа.

### Пример настройки (application.yml)

```yaml
resilience4j.circuitbreaker:
instances:
productService:
slidingWindowSize: 10              
failureRateThreshold: 50           
waitDurationInOpenState: 30s       
permittedNumberOfCallsInHalfOpenState: 3
```

### Когда НЕ нужен Fallback
Если данные критически важны (например, нельзя добавить товар в корзину, не проверив его наличие), fallback не нужен. В этом случае CB просто защищает твой сервис от зависания, выдавая ошибку быстро.

```java

@CircuitBreaker(name = "productService")
public Flux<ProductFullResponse> getProductAllByIds(List<Long> productIds) {
    log.info("Trying to get a list of products {}", productIds);
    return productWebClient.get()
            .uri(uriBuilder -> uriBuilder
                    .path("/api/v1/products")
                    .queryParam("ids", productIds)
                    .build())
            .retrieve()
            .bodyToFlux(ProductFullResponse.class);
}

@Transactional
public Mono<CartItem> addItem(Long userId, Long productId, int quantity) {
return productClient.getProductAllByIds(List.of(productId))
.singleOrEmpty()
.switchIfEmpty(Mono.error(new NotFoundException("error.product.notfound", productId)))
.flatMap(product -> {
int initialQty = Math.min(quantity, product.quantity());
return cartItemRepository.findByUserIdAndProductId(userId, productId)
.flatMap(cartItem -> {
cartItem.setQuantity(Math.min(cartItem.getQuantity() + quantity, product.quantity()));
return cartItemRepository.save(cartItem);
})
.switchIfEmpty(Mono.defer(() -> cartItemRepository.save(new CartItem(null, userId, productId, initialQty, true, null))));
});
}
```

Применение заглушки здесь, нецелесообразно потому что:

* **Нарушение логики:** Если productService недоступен, вы не знаете актуальную цену товара, его наличие или вообще существует ли он. Если заглушка вернет «пустой список» или «дефолтный товар», вы добавите в корзину «пустоту» или некорректные данные.
* **Целостность данных:** Для операции addItem отсутствие информации о продукте — это критическая ошибка. В этом случае 500 ошибка (или 503 Service Unavailable) — это честный ответ системы: «Я не могу выполнить действие, потому что внешние данные недоступны».

В этом случае @CircuitBreaker нужен не для того, чтобы «спасти» пользователя от ошибки, а чтобы защитить систему:
* **Fail Fast (Быстрый отказ):** Когда productService начнет тормозить (например, отвечать по 30 секунд), Circuit Breaker «разомкнется». Следующие запросы в addItem будут падать мгновенно, не дожидаясь таймаутов. Это спасет ваши потоки (threads) и ресурсы от зависания.
* **Снятие нагрузки:** Вы перестанете «доливать масло в огонь», отправляя запросы на уже упавший сервис, давая ему время восстановиться.

Поэтому стоит лишь добавить ControllerAdvice, который будет ловить CallNotPermittedException и превращать его, в чистый 503 Service Unavailable вместо стандартной 500-й.

В итоге, без заглушки, когда CB разомкнут:
1. Вызывается addItem.
2. productClient.getProductAllByIds мгновенно выбрасывает CallNotPermittedException.
3. Реактивная цепочка прерывается.
4. Транзакция откатывается (если она была начата).
5. Пользователь получает ошибку.

* **Резюме:** Для записи/изменения данных (как в корзине) отсутствие заглушки — это нормально. Заглушки обычно ставят на чтение (Read), где можно показать старые данные, но редко на запись (Write).





## <a id="outbox-p">Outbox</a>

Разберем «на пальцах», от какой катастрофы спасает этот паттерн.

### Проблема: «Разрыв транзакции»

Представь, что ты НЕ используешь Outbox, а просто шлешь сообщение в Кафку прямо из сервиса:

#### Сценарий А (Сначала база, потом Кафка)

1. Сервис сохранил заказ в БД.
2. Сервис пытается отправить сообщение в Кафку, но интернет мигнул или Кафка на секунду зависла.

**Итог:** Заказ в базе есть, но Кафка о нем не знает. Корзина не очистится, склад не обновится. Юзер видит заказ, но система «сломалась».

#### Сценарий Б (Сначала Кафка, потом база)

1. Сервис отправил сообщение в Кафку.
2. Сервис пытается сохранить заказ в БД, но база выдает ошибку (например, дубликат ID).

**Итог:** Заказа в базе нет (откат), но Кафка уже получила сигнал! Корзина очистится, склад спишется — а заказа не существует. Деньги улетели в никуда.

### Как спасает Outbox Pattern?

Мы используем `атомарность БД.` Мы записываем заказ и сообщение в одну «коробку» (транзакцию).

1. Если база приняла заказ — она 100% приняла и запись в outbox_events.
2. Если база отклонила заказ — запись в outbox_events тоже не появится.

**Итог:** Теперь у нас в базе лежит «письмо», которое гарантированно соответствует заказу. Нам остается только взять его и переложить в Кафку. Даже если интернет пропадет на час, письмо никуда не денется из базы.

## <a id="saga-p">Распределенные транзакции: Saga</a>

В микросервисах нет единой транзакции на два сервиса. Если мы списали товар в Product-Service, но Order-Service не смог сохранить заказ в свою БД (например, диск переполнился), товар «зависнет» — его нет на складе, и его никто не купил.

### Как делать компенсацию:
Это обычный UPDATE, который просто прибавляет количество назад. В Order-Service мы ловим ошибку и посылаем запрос «верни всё как было».

### Золотое правило микросервисов:

* **Локальная компенсация (Quick Rollback):** Если ты в одном методе вызвал Product-Service (списал), а потом твоя база Order-Service упала — ты тут же в onErrorResume вызываешь Product-Service (вернуть), потому что ты «хозяин» этой операции в данный момент. Это быстро и надежно.
* **Распределенная компенсация (Saga):** Если заказ успешно создался и ты «отпустил» клиента, а через 5 минут Payment-Service прислал в Кафку сообщение «Оплата не прошла» — вот тут Order-Service (или сам Product-Service) ловит это событие и делает возврат товара.

Это разделяет ошибки программирования/базы (которые чиним сразу) и бизнес-ошибки (отказ оплаты, нет на складе), которые чиним через события.


## Out of scope - границы MVP

**Out of scope** (вне границ) — это функциональность, которую мы сознательно НЕ включаем в первую версию микросервисной архитектуры.

### Зачем это нужно?

* Нельзя перевести весь монолит сразу — это слишком рискованно и долго
* Нужно выбрать первую цель — сервис, который принесет максимальную пользу
* Часть функциональности остается в монолите (на время)
* Часть может быть вообще не нужна в новой архитектуре

### Типичные критерии:

* Редко используемые функции
* Административные интерфейсы (низкая нагрузка)
* Сложные отчеты
* Легаси-данные
* Функции требующие слоожной миграции данных

*MVP (Minimum Viable Product)* определение границ микросервисов — это баланс между скоростью запуска и будущей масштабируемостью.

Каждый сервис должен отвечать за одну бизнес-область.

* Если при изменении логики склада приходится переписывать код в сервисе продаж — границы расставлены неверно.
* Single Responsibility (Единая ответственность) - Если логика «засоряет» модель данных другого процесса, ее пора выделять

* Сильная связность внутри — все, что нужно для работы с заказами, в одном месте
* Слабая связанность - Независимость — Order Service может менять логику, не ломая Catalog. Если мы хотим поменять логику заказа, при этом деплоим функционал каталога - присутствует сильная связанность.

*Пример:*

Могу ли я полностью переписать внутренности сервиса «Склад» (например, заменить SQL на NoSQL), не уведомляя об этом разработчиков сервиса «Продажи»?
Если ДА — границы верные.
Если НЕТ (сломаются контракты, зависимости) — сервисы слишком связаны.

## Способы декомпозиии микросервисов

Как только зависимость от данных уменьшается, меньше используются выделенным функционалом - признак того, что границы меняются.
Если зависимость большая, сервисам придется часто обращаться к друг к другу - признак того что неправильно, сильно мелко, определили границы.

### По Бизнес-возможностям

Вынесение функционала в отдельные микросервисы.

Один микросервис - одна функция, которой пользуются другие сервисы. Сервис платежей, Сервис уведомлений, Сервис генерации PDF.

Представляет собой список функций(глаголов), граница там где заканчивается действие.

*Плюсы:*

* Переиспользование — один сервис для многих потребителей
* Можно масштабировать независимо (например, 10 экземпляров Payment Service)
* Четкая единая точка изменений

### По доменам

В рамках **DDD (Domain-Driven Design)**, каждый домен определяется своим уникальным языком(Ubiquitous Language).
Под одним и тем же словом, могут понимать разные вещи - это значит это разные домены.
В каком то домене слово есть, а в каком-то его нет.

#### Основные принципы:
*   **Общий словарь:** Разработчики, менеджеры и эксперты (Domain Experts) используют одни и те же термины.
*   **Код как отражение реальности:** Названия сущностей, методов и событий в коде (например, `OrderConfirmed`, `PlaceOrder`) должны соответствовать бизнес-языку.
*   **Устранение трудностей перевода:** Исчезает необходимость «переводить» требования заказчика на технический язык программиста.
*   **Контекстная зависимость:** Язык уникален внутри конкретного **Bounded Context**. Одно и то же слово (например, «Аккаунт») может иметь разные значения в контексте *Биллинга* (составления счета) и *Поддержки*.
Внутри контекста "Товар" - это описание и цена. Снаружи (на Складе) этот же "Товар" — это габариты и остаток на полке.
**Это разные модели**, хотя в реальности это одна вещь.

Группировка связанного с сущностью функционала, по границам ответственности. Один сервис отвечает за все что связано с его доменом.

Один микросервис — вся логика для одной бизнес-области. Catalog Service (категории + товары + свойства + фильтрация)

Представляет собой список сущностей (существительных), граница там, где меняется смысл этого слова, как отдел работает с сущностью, какие функции и свойства используется.
Весь не нужный отделу функционал(например по скалду для отдела продаж - выносится).

Границы домена определяются по правилу «один ответственный, один язык, независимость изменений».

#### Применяю подход по доменам потому-что:

* Чтобы сильно не мельчить сервисы - сложность в управлении, поднятие инфраструктуры.
* Чтобы отделы могли в одном месте выполнять большую часть функционала, связанного общими данными. (консультанты с катологм, менеджеры с заказом)
* Минимизируем распределенные транзакции(большенство внутри одного сервиса).
* Между доменами только слабые связи. (сильные, часто запрашиваемые JOIN остаются внтури)
* Проще в разработке.
* Меньше сетевых вызовов и точек отказа.

Мы выбрали декомпозицию по доменам (Bounded Context), потому что она лучше отражает структуру бизнеса и данные.
Catalog Service отвечает за все, что связано с товарами и каталогом.
Order Service — за все, что связано с заказами.
Это дает сильную связность внутри сервиса и слабую связанность между ними.

Сервисы по бизнес-способностям мы тоже будем использовать, но для сквозных функций, которые нужны нескольким доменам — например, уведомления или платежи.
Они не хранят свои данные (или хранят минимум), а только выполняют операции по запросу.

# Фронтенд: Thymeleaf + BFF (Backend for Frontend)

### Проблема: Thymeleaf не дружит с микросервисами
**Как работает Thymeleaf:**
* Контроллер и HTML-шаблон должны быть в одном сервисе.
* В микросервисной архитектуре каждый сервис должен был бы иметь свои шаблоны.
* → дублирование layout'ов (header, footer, css)
* → разные стили
* → медленная навигация (перезагрузка при переходе между сервисами)

---

### Решение: BFF (Backend for Frontend)
#### Архитектура с BFF:

[Браузер] (пользователь)
↓
[API Gateway] (маршрутизация, аутентификация, rate limiting)

### Как работает BFF
Все запросы от браузера идут в BFF через Gateway.

# Gateway routes
spring:
cloud:
gateway:
routes:
- id: bff
uri: lb://bff-service
predicates:
- Path=/**

BFF содержит все Thymeleaf-контроллеры и шаблоны:

@Controller
@RequestMapping("/products")
public class ProductPageController {

    private final CatalogServiceClient catalogClient;  // REST клиент
    
    @GetMapping("/{id}")
    public String productPage(@PathVariable Long id, Model model) {
        // Вызов микросервиса по REST
        ProductDto product = catalogClient.getProduct(id);
        model.addAttribute("product", product);
        return "product/product";  // шаблон здесь
    }
}

BFF может собирать данные из нескольких микросервисов:

@GetMapping("/product/{id}")
public String productPage(@PathVariable Long id,
@AuthenticationPrincipal UserDetails user,
Model model) {

    // 1. Данные о товаре из Catalog Service
    ProductDto product = catalogClient.getProduct(id);
    
    // 2. Проверка корзины из Basket Service
    if (user != null) {
        boolean inBasket = basketClient.isInBasket(user.getId(), id);
        model.addAttribute("inBasket", inBasket);
    }
    
    // 3. Отзывы из Review Service (будущее)
    List<ReviewDto> reviews = reviewClient.getReviews(id);
    
    model.addAttribute("product", product);
    model.addAttribute("reviews", reviews);
    
    return "catalog/product";
}

### Gateway + BFF: схема взаимодействия

[Браузер] → 1 запрос
↓
[Gateway] → 1 запрос (прокси)
↓
[BFF] → несколько внутренних запросов (REST)
↓
├──→ User (JSON)
├──→ Catalog (JSON)
└──→ Basket (JSON)
↓
[BFF] → 1 HTML ответ
↓
[Браузер] ← отрисованная страница

---

### Преимущества подхода
* ✅ Для пользователя: Быстрая загрузка (1 запрос = 1 страница), единый стиль, сессии работают как в монолите.
* ✅ Для разработки: Можно постепенно выносить логику в микросервисы, Thymeleaf-шаблоны не дублируются, микросервисы простые (только JSON).
* ✅ Для инфраструктуры: Gateway ничего не знает про бизнес-логику, легко масштабировать BFF, микросервисы можно переписывать независимо.

### Что остается в монолите:
* Админка (пока)
* Старые данные
* Монолит больше не рендерит пользовательские страницы

### План миграции:
1. Шаг 1: Создать BFF Service — скопировать туда все контроллеры и шаблоны.
2. Шаг 2: Переписать контроллеры на вызовы REST-клиентов.
3. Шаг 3: Постепенно выносить логику в микросервисы.
4. Шаг 4: Gateway направляет все запросы в BFF.
