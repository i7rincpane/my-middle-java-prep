## <a id="primary-keys-p">Классификация первичных ключей (Primary Keys)</a>

```java


package ru.nvkz.common;

import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import io.micrometer.observation.contextpropagation.ObservationThreadLocalAccessor;
import io.micrometer.tracing.Span;
import io.micrometer.tracing.TraceContext;
import io.micrometer.tracing.Tracer;
import io.micrometer.tracing.propagation.Propagator;
import lombok.RequiredArgsConstructor;
import org.apache.kafka.clients.producer.ProducerRecord;
import reactor.core.publisher.Mono;

import java.util.HashMap;
import java.util.Map;
import java.util.function.Supplier;


@RequiredArgsConstructor
public class ReactiveTraceExecutor {

    private final Tracer tracer;
    private final Propagator propagator;
    private final ObservationRegistry observationRegistry;


    /**
     * НАЗВАНИЕ: Выполнить со следующим Kafka-спаном
     * СМЫСЛ: Используется на стороне ОТПРАВИТЕЛЯ (Producer / Scheduler).
     * Метод берет старые ID из БД, делает текущий сервис "родителем", создает
     * новую операцию (Next Span) и вшивает её заголовки в исходящее сообщение Kafka.
     * 1. Восстанавливаем родительский контекст (parentContext) из сохраненных в БД traceId и spanId.
     * 2. Создаем заготовку спана билдером (через tracer.spanBuilder()), указав восстановленный контекст как "родителя".
     * 3. Создаем обсервер (observation).
     * 4. Запускаем спан (parentSpan) и временно кладем его в tracer (в ThreadLocal поток Java), чтобы сделать активным.
     * 5. Обсервер при старте (observation.start()) заглядывает в tracer, видет запущенный спан, связывает себя с его Trace ID и запускает метрики (таймер).
     * 6. Извлекаем текущий склеенный ID из трейсера и принудительно вшиваем его в заголовки исходящего сообщения Kafka (propagator.inject).
     * 7. Передаем обсервер в реактивный контекст (.contextWrite) внутренней бизнес-цепочки, чтобы логи (MDC) работали.
     * 8. Когда вся цепочка отправки отработала: таймер остановили (observation.stop()), а спан, созданный нами вручную, удалили из памяти (.end()).
     */
    public <T> Mono<T> executeWithNextKafkaSpan(
            String traceId,
            String spanId,
            String operationName,
            ProducerRecord<String, String> kafkaRecord,
            Supplier<Mono<T>> reactiveAction
    ) {
        // 1. Восстанавливаем родительский контекст из БД, чтобы связать разорванную шедулером цепь
        TraceContext parentContext = tracer.traceContextBuilder()
                .traceId(traceId)
                .spanId(spanId)
                .sampled(true)
                .build();

        /*
          2. Создаем Observation. В реактивном контексте автоматическое копирование (MDC логов)
          завязано на него, сам создает метрики (замеры для Grafana) и спаны (для Zipkin).
         */
        Observation observation = Observation.createNotStarted(operationName, observationRegistry);

        // Сбрасываем пустой контекст планировщика, чтобы не было ложных связей с системными процессами
        observation.parentObservation(null);

        // Ленивое реактивное выполнение — запустится строго в момент подписки (.subscribe())
        return Mono.defer(() -> {

            // ИСПРАВЛЕНО: Запуск спана перенесен внутрь defer, чтобы он стартовал строго в момент отправки
            Span parentSpan = tracer.spanBuilder().setParent(parentContext).start();

            /*
              withSpan кладет этот восстановленный спан в ThreadLocal текущего потока шедулера,
              чтобы выполняемый ниже observation.start() "увидел" родительский Trace ID.
              Синхронный try-блок закроется и очистит ThreadLocal мгновенно, предотвращая "залипание" ID в пуле.
             */
            try (Tracer.SpanInScope parentScope = tracer.withSpan(parentSpan)) {

                observation.start(); // Смотрит, что включен Zipkin, запускает таймер и создает спан публикации

                // Приводим ID к шаблону и добавляем в бинарные заголовки (traceparent) исходящего сообщения Kafka
                propagator.inject(tracer.currentSpan().context(), kafkaRecord,
                        (rec, key, val) -> rec.headers().add(key, val.getBytes()));

                // Выполняем бизнес-логику (непосредственную отправку записи в Кафку через KafkaSender)
                return reactiveAction.get()
                        /*
                          Этот внутренний contextWrite гарантирует, что Trace ID будет в логах логгера
                          для ВСЕХ операторов внутри reactiveAction
                         */
                        .contextWrite(ctx -> ctx.put(ObservationThreadLocalAccessor.KEY, observation))
                        // Асинхронная очистка ресурсов строго по завершении сетевой работы Кафки
                        .doFinally(signal -> {
                            observation.stop(); // Закрывает спан публикации и шлет замеры в Zipkin
                            parentSpan.end();   // Очищает память Brave от родительского спана-декоратора
                        });
            }
        });
    }


    /**
     * НАЗВАНИЕ: Выполнить как потребитель Kafka
     * СМЫСЛ: Используется на стороне ПОЛУЧАТЕЛЯ (Consumer / @KafkaListener).
     * Метод не знает никаких ID заранее. Он берет входящие бинарные заголовки сообщения,
     * достает из них сохраненный traceparent, восстанавливает дерево трассировки
     * и делает текущий метод ребенком (продолжением) асинхронной цепочки.
     * 1. Создали заготовку спана билдером (spanBuilder).
     * 2. Запустили этот спан (tempSpan) и положили его в tracer (в поток), чтобы сделать активным.
     * 3. Создали обсервер (observation).
     * 4. Обсервер при старте заглянул в tracer, увидел запущенный спан, забрал его traceId и запустил метрики (таймер).
     * 5. Передали обсервер в реактивный контекст(contextWrite) бизнесс цепочки (у каждой цепочки свой реактивный контекст).
     * 6. Когда вся цепочка отработала: таймер остановили(stop), а спан, созданный нами вручную, удалили из памяти (.end()).
     */
    public <T> Mono<T> executeAsKafkaConsumer(
            org.apache.kafka.common.header.Headers kafkaHeaders,
            String operationName,
            String contextualName,
            String topic,
            Supplier<Mono<T>> reactiveAction
    ) {

        /* Kafka передает данные по сети в виде байт-массивов (byte[]).
   Чтобы Micrometer смог прочитать заголовки трассировки (например, "traceparent"),
   мы преобразуем бинарные заголовки Kafka в стандартную текстовую Map<String, String>.
   */
   Map<String, String> headersMap = new HashMap<>();
   kafkaHeaders.forEach(h -> headersMap.put(h.key(), new String(h.value())));

        /* 2. ВОССТАНОВЛЕНИЕ КОНТЕКСТА (Extraction)
   Propagator - это парсер сетевых стандартов (W3C или B3). Он заходит в нашу текстовую headersMap,
   ищет там строку вроде "traceparent: 00-6a0b44...-b60ab...-01" и достает из нее оригинальные
   идентификаторы Trace ID и Parent Span ID.
   Метод возвращает Span.Builder - заготовку для нового Спана, в которую УЖЕ вшит родительский ID.
   */
   Span.Builder spanBuilder = propagator.extract(headersMap, Map::get);


    /* 3. СОЗДАНИЕ НАБЛЮДАТЕЛЯ (Observation)
      Мы instrument-ируем (помечаем) код один раз через Observation, а Spring под капотом подключает
      к ней 3 слушателя:
        - Слушатель трассировки: автоматически создаст для Zipkin.
        - Слушатель метрик: начнет замерять время выполнения для Prometheus (миллисекунды).
        - Слушатель логов: свяжет это наблюдение со встроенной системой логирования (MDC).
      createNotStarted - создает эту обертку, но пока не запускает часы (таймер).
      lowCardinalityKeyValue — добавляет постоянный тег для метрик.
     */

        Observation observation = Observation.createNotStarted(operationName, observationRegistry)
                .contextualName(contextualName)
                .lowCardinalityKeyValue("kafka.topic1", topic);

          /* 4. Spring может попытается сделать наш новый бизнес-спан ребенком, случайного системного процесса.
      Вызовом parentObservation(null) мы принудительно очищаем иерархию НАБЛЮДЕНИЙ, гарантируя,
      что наше бизнес-действие начнется с чистого листа на уровне Observation.
     */
        observation.parentObservation(null);

           /* 5. ЛЕНИВАЯ ИНИЦИАЛИЗАЦИЯ (Project Reactor)
      Mono.defer: Реактор не выполняет код внутри прямо сейчас.
      Ожидается пока консьюмер Кафки физически не подпишется (.subscribe()) на этот поток.
      Это гарантирует, что Спан откроется строго в миллисекунду реального старта обработки сообщения.
     */
        return Mono.defer(() -> {

               /* 6. СТАРТ ВРЕМЕННОГО СПАНА (Декоратор/Мост)
          У нас есть заготовка spanBuilder (содержит ID из Кафки). Но Observation.start() ничего не знает про Кафку.
          Поэтому мы вынуждены запустить временный спан (tempSpan) из этой заготовки.
          Его единственная цель, на долю секунды подержать в себе Trace ID, который пришел из сети.
         */
            var tempSpan = spanBuilder.start();

             /*
           7. АКТИВАЦИЯ КОНТЕКСТА В ПОТОКЕ (ThreadLocal)
           Метод observation.start() внутри себя лезет в текущий поток Java (в ThreadLocal)
           и спрашивает у трассировщика активный спан.
           Конструкция tracer.withSpan(tempSpan) кладет наш временный спан в ThreadLocal текущего потока.
           Благодаря этому, когда строчкой ниже вызывается observation.start(), Наблюдатель заглядывает
           в поток, находит там наш tempSpan, копирует из него оригинальный Trace ID и продолжает эту цепочку, а не генерирует новый ID.
          */
            try (Tracer.SpanInScope ps = tracer.withSpan(tempSpan)) {

                observation.start(); // Запускает таймер метрик и создает в Zipkin дочерний спан "продолжения" трассы

                /*
              Мы вызываем reactiveAction.get() - это тело слушателя (чтение JSON, clearCart, onErrorResume).
              try-with-resources выполняется синхронно, мгновенно закрывает и стирает
              данные из ThreadLocal.
              А реактивный поток бизнес-логики будет выполняться асинхронно, прыгая по разным потокам Netty.
              Оператор .contextWrite() берет наш настроенный объект observation и пришивает его к Реактивному Контексту.
              Теперь, когда Reactor будет переходить от оператора к оператору (например, упадет в .onErrorResume),
              он будет смотреть в Реактивный Контекст, находить там нашу observation, НА СЕКУНДУ открывать её Scope
              для логгера (MDC) и закрывать.
              Благодаря этому ЛЮБОЙ логгер (даже логгер ошибок) увидит Trace ID, несмотря на то, что синхронный try давно закрыт!
             */
                return reactiveAction.get()
                        // Проброс ID в MDC реактивных операторов. Извлекает новый-дочерний Trace ID из нашей observation
                        // и прописывает его в MDC текущего потока Netty/Reactor
                        // для ВСЕХ операторов внутри reactiveAction (включая .onErrorResume)
                        .contextWrite(ctx -> ctx.put(ObservationThreadLocalAccessor.KEY, observation))
                        // Гарантированная очистка ресурсов согласно спецификации Micrometer Tracing
                        .doFinally(signal -> {
                            observation.stop(); // Останавливает таймер метрик, закрывает внутренний спан и отправляет его в Zipkin

                            // ОСВОБОЖДЕНИЕ ПАМЯТИ: Зачем вызывать end()?
                            // Блок try-with-resources в Java автоматически закрывает ТОЛЬКО объект SpanInScope (очищает поток).
                            // Но сам Java-объект tempSpan остается жить в оперативной памяти трекера Brave как "незавершенный".
                            // Вызов tempSpan.end() — это жесткая команда: «Уничтожь этот спан-декоратор из памяти Brave».
                            // Без этой строки при обработке миллионов сообщений приложение упадет с OutOfMemoryError.
                            tempSpan.end();
                        });
            }
        });
    }


}
```

## 1. Архитектура: Гибридный стек (JDBC + R2DBC)

В реактивном приложении мы используем два разных драйвера для одной базы данных.

| Компонент  | Технология | Роль |
|------------|------------|------|
| Liquibase  | JDBC (Блокирующий) | Выполняет миграции (DDL) строго при старте приложения. |
| Приложение | R2DBC (Реактивный) | Выполняет бизнес-запросы (DML) неблокирующим способом. |

**Почему нужен конфигурационный класс?**  
Spring Boot в реактивном режиме (WebFlux) игнорирует автонастройку JDBC. Чтобы Liquibase заработал, мы вручную создаем бин `DataSource` (через `DriverManagerDataSource` из `spring-jdbc`), который берет параметры из `application.yaml`.

## 2. Testcontainers: Изоляция и Порты

**Суть:** Для каждого запуска тестов Docker поднимает абсолютно чистую базу.

### Проброс портов (Port Forwarding)
- **Внутренний порт (5432):** Статичен. Postgres внутри контейнера всегда слушает его.
- **Внешний порт (напр. 32789):** Динамический. Docker выбирает случайный свободный порт на твоем компьютере.

**Зачем динамика?** Чтобы избежать конфликтов, если параллельно идут два теста или если на ПК уже запущена другая база на 5432.

### DynamicPropertyRegistry
Это «динамический application.yaml» в памяти. Мы берем случайный порт от Docker и записываем его в настройки Spring:
- `spring.datasource.url` (для Liquibase/JDBC)
- `spring.r2dbc.url` (для приложения/R2DBC)

## 3. Реактивный мир: Netty и WebTestClient

### Netty vs Tomcat
- **Tomcat (Servlet):** Один запрос = Один поток. Если поток ждет базу, он "заблокирован".
- **Netty (WebFlux):** Работает на Event Loop. Поток принимает запрос, отдает команду базе и тут же идет принимать следующий запрос. Когда база ответит, Netty вернется и допишет ответ пользователю.

### WebTestClient
Это специальный реактивный клиент для тестов.
- Он умеет "подписываться" на Flux и Mono.
- В Spring Boot 4.0 он вынесен в отдельный модуль:  
  `testImplementation 'org.springframework.boot:spring-boot-webtestclient'`.
- Аннотация `@AutoConfigureWebTestClient` заставляет Spring создать этот "браузер" и нацелить его на `RANDOM_PORT` приложения.

### Зачем .block() в тестах?
В приложении блокировать потоки нельзя. Но в тестах JUnit идет выполнение сверху вниз. Чтобы база успела сохранить данные до того, как мы их запросим, мы вызываем `.block()`, заставляя тест дождаться результата.

## 3. Реактивный мир: Netty, WebTestClient и Потоки

### Netty vs Tomcat
*   **Tomcat (Servlet API):** Использует модель «один запрос = один поток». Если база данных отвечает долго, поток «блокируется» (простаивает), потребляя память (около 1 МБ на поток). При высокой нагрузке потоки заканчиваются, и приложение перестает отвечать.
*   **Netty (WebFlux):** Работает на Event Loop (как Node.js). Один поток может обрабатывать тысячи соединений. Он не ждет ответа от БД, а переключается на другие задачи. Когда данные из БД готовы, Netty получает уведомление и отправляет результат.

### WebTestClient
Это основной инструмент для тестирования реактивных систем.
*   **Асинхронность:** Он умеет «подписываться» на `Flux` и `Mono`, не блокируя выполнение теста.
*   **Зависимость:** В Spring Boot 4.0 включен в стартер или добавляется отдельно:  
    `testImplementation 'org.springframework.boot:spring-boot-starter-webflux'`.
*   **Автоконфигурация:** Аннотация `@AutoConfigureWebTestClient` автоматически создает клиент, настроенный на порт вашего тестового контейнера.

### Flux vs Mono: Не только асинхронность, но и Стриминг
Реактивность — это не просто «не ждать ответа», это возможность работать с данными **потоково** (streaming).

*   **Mono<T>:** 0 или 1 элемент. Используется для одиночных объектов (например, `findById`).
*   **Flux<T>:** 0...N элементов. Поток данных, который может быть бесконечным.

**В чем разница с обычным List?**
1.  **Память:** В обычном MVC вы сначала выкачиваете 100 000 строк из БД в `List` (забивая RAM), и только потом отдаете клиенту. Во WebFlux + R2DBC данные текут транзитом: первая строка пришла из базы — и тут же улетела клиенту. Приложение — это просто «труба».
2.  **Backpressure (Обратное давление):** Если клиент (браузер) медленный, `Flux` скажет базе данных: «Притормози, не выгружай новые строки, мы не успеваем их отправлять».

### Зачем .block() в тестах?
В самом приложении вызывать `.block()` категорически **запрещено** (это убивает смысл реактивности). Однако в тестах это допустимо:
*   Чтобы превратить `Mono<User>` в реальный объект для проверки через `assertEquals`.
*   Чтобы тест «подождал» завершения фоновой операции перед тем, как делать проверки в БД.
*   **Важно:** Если используете `WebTestClient` или `StepVerifier` (из `reactor-test`), вызывать `.block()` не нужно — они «подписываются» на поток сами.

### Пагинация в реактивном мире
Даже если `Flux` умеет стримить миллионы записей, пагинация (`Pageable`) все равно нужна.
*   **Зачем:** Чтобы ограничить нагрузку на саму БД (Disk I/O и CPU).
*   **Как работает:** Мы запрашиваем страницу (например, 20 записей), но внутри этой страницы данные все равно обрабатываются реактивно — по одному объекту за раз, а не всей пачкой.

### 4. Концепция: Курьер vs Конвейер

Чтобы понять разницу между обычным подходом (`List`) и реактивным (`Flux`), используй аналогию с едой:

*   **Mono<List> (Курьер):** Вы заказываете 50 пицц для вечеринки. Курьер приедет только тогда, когда в пекарне приготовят **все 50**. Вам нужен огромный стол (RAM), чтобы всё это расставить, и вы всё это время сидите голодными.
*   **Flux (Конвейер):** Это суши-робот или конвейер. Как только один ролл готов — он едет к вам. Вы начинаете есть (обрабатывать данные) мгновенно. Вам не нужен большой стол — поели один, приехал второй.

### Как работают потоки (Threads) под капотом?
Многие думают, что реактивность — это когда на каждый `.map()` создается новый поток. Это не так.

1.  **Цепочка — это чертеж:** Когда вы пишете `.map().filter()`, вы не выполняете код, а строите «трубопровод».
2.  **Поток-носитель:** Когда данные (элемент) поступают из базы, их подхватывает свободный поток Netty. Он «несет» этот элемент через всю вашу трубу (через все map и filter).
3.  **Неблокирующее ожидание:** Если на пути встречается операция ввода-вывода (запись в другую БД), поток не «засыпает». Он регистрирует обратный вызов (callback) и уходит обслуживать другие элементы или запросы. Когда БД ответит, **любой** свободный поток Netty подхватит результат и понесет его дальше по трубе.

**Итог:** Реактивность позволяет обрабатывать огромные потоки данных, используя всего 4–8 потоков процессора, потому что ни один из них никогда не стоит без дела.


### 4. Кто именно обрабатывает элементы? (Магия Event Loop)

Многие путают «реактивность» с «многопоточностью». На самом деле, реактивность — это **максимально плотная загрузка** небольшого количества потоков (обычно их столько же, сколько ядер у CPU).

#### Как элементы движутся по потокам (Threads):
Представь 4-ядерный процессор (4 потока Netty: А, Б, В, Г) и базу данных, из которой вылетает `Flux<User>` с 100 записями.

1.  **Параллельная обработка:**
    *   **Поток А** хватает Юзера №1 и тащит его через твой `.map()`.
    *   В это же время **Поток Б** хватает Юзера №2 и прогоняет через `.filter()`.
    *   Они работают **одновременно**. Реактивность позволяет разным ядрам процессора обрабатывать разные части одного и того же потока данных.

2.  **Переключение задач (Context Switching):**
    *   Если **Поток А** отправил Юзера №1 в сетевой сокет (отдал клиенту), он не ждет подтверждения «ОК, я получил».
    *   Он мгновенно забывает про Юзера №1 и берет из очереди Юзера №5. Поток никогда не «спит» и не блокируется.

3.  **Гарантия порядка (Ordering):**
    Это самый важный момент. Представь, что Юзер №1 — «тяжелый» (сложный маппинг), а Юзер №2 — «легкий».
    *   **Поток Б** закончил обработку Юзера №2 быстрее, чем **Поток А** закончил с Юзером №1.
    *   **Reactor сам проследит за очередью:** Он придержит готового Юзера №2 «в предбаннике», пока Юзер №1 не будет готов к отправке.
    *   **Итог:** Клиент в браузере всегда получит данные строго в том порядке, в котором их выдала база (1, потом 2, потом 3), даже если внутри приложения они обрабатывались вразнобой разными ядрами.

#### Почему это лучше обычного подхода?
*   **В обычном приложении (Tomcat):** Один поток «приклеен» к одному пользователю. Если пользователь медленно качает данные, поток сидит и ждет его. При 200 таких пользователях приложение «встает», хотя процессор свободен.
*   **В реактивном приложении (Netty):** Потоки — это быстрые «официанты». Они не стоят у столика, пока клиент жует. Они поставили тарелку — и убежали к другому столику. Один официант может обслуживать 1000 клиентов одновременно.

#### Коротко для запоминания:
*   **Один элемент** = обрабатывается одним потоком в конкретный момент времени (без гонок данных внутри элемента).
*   **Разные элементы одного Flux** = могут обрабатываться разными потоками параллельно.
*   **Порядок** = Reactor гарантирует, что на выходе из «трубы» все элементы выстроятся в исходную очередь.




## Архитектурная схема: Как устроен алгоритм работы Debezium?Схема взаимодействия компонентов выглядит следующим образом:[ order-service ]
       │
(1) INSERT INTO outbox_events (сохранение заказа в бизнес-транзакции)
▼
[ order_service_db (Postgres) ] ───(2) Пишет бинарную строку───► [ WAL-лог (Logical) ]
│
(3) Слушает бинарный поток
▼
[ Debezium ]
│
(4) Превращает в JSON
и пушит событие
▼
[ Кафка (Broker) ]
│
┌─────────────────────┴─────────────────────┐
▼                                           ▼
Служебные топики Debezium                       Твой тестовый топик
(создаются им автоматически)                    (куда прилетел твой JSON)
- `my_connect_configs`                          - `cdc.public.outbox_events`
- `my_connect_offsets`
- `my_connect_statuses`
Бизнес-код делает обычный INSERT в таблицу outbox_events.Postgres перед записью на диск фиксирует это действие в системном бинарном WAL-логе в режиме logical.Debezium, подключенный через слот репликации, непрерывно «читает» этот WAL-лог.Debezium преобразует байты в JSON и отправляет его в топик Кафки, который он формирует сам по шаблону: префикс.схема.таблица (cdc.public.outbox_events) [INDEX: 15].Служебные топики: Те топики, которые ты увидел в Кафке (my_connect_...), Debezium создал для себя [INDEX: 15]. Он записывает туда свои настройки и бинарные смещения (какую строчку WAL-лога он прочитал последней). Если Дебезиум перезагрузится, он заглянет в my_connect_offsets и поймет, откуда продолжать читать Postgres.
