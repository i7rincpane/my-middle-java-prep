## <a id="producer-p">Producer Configuration</a>

### MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION

Параметр определяет, сколько запросов (батчей) продюсер может отправить брокеру, **не дожидаясь подтверждения** (ack) о
получении предыдущих.

* **Зачем:** Увеличивает пропускную способность (throughput), позволяя «забивать» сетевой канал данными непрерывно.
* **Риск:** Без дополнительных настроек может нарушиться порядок сообщений при ошибках и повторах (retries).

### Idempotence & Ordering

Чтобы не жертвовать скоростью ради порядка, используется **Идемпотентность** (`enable.idempotence=true`).

### Как это работает:

1. **Sequence Numbers:** Брокер присваивает каждому батчу номер. Если батч №2 пришел раньше №1, брокер его не примет,
   пока не получит №1.
2. **Гарантия порядка:** При включенной идемпотентности можно смело ставить `MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION` до *
   *5** (максимальное стабильное значение).
3. **Результат:** Высокая скорость + гарантия, что сообщения лягут в партицию ровно в том порядке, в котором их отправил
   продюсер.

### Сценарий сбоя:

Если из 5 «летящих» батчей первый упал по сети, а остальные 4 долетели:

* Брокер их отклонит (OutOfOrderSequenceException).
* Продюсер переотправит всю пачку.
* Благодаря ID продюсера и номерам последовательности, брокер запишет их строго по порядку и **без дублей**.

## <a id="durability-p">Durability & Acks</a>

Параметр **`acks`** (acknowledgments) определяет, сколько реплик должны подтвердить получение сообщения, прежде чем
Продюсер посчитает отправку успешной.

### acks=all (или -1)

Это самый надежный режим. Лидер партиции ждет подтверждения от **всех** синхронизированных реплик (**ISR** — In-Sync
Replicas).

* **Плюс:** Максимальная сохранность данных. Если лидер упадет сразу после записи, данные уже есть на других брокерах.
* **Минус:** Самая высокая задержка (latency), так как мы ждем ответа от нескольких серверов по сети.

### Связка с min.insync.replicas

`acks=all` работает по-настоящему только в паре с настройкой брокера `min.insync.replicas`.

* **Как это работает:** Если `min.insync.replicas=2`, а `acks=all`, то запись будет успешной только если **минимум 2
  реплики** (лидер + 1 фолловер) подтвердили получение.
* **Защита:** Если в живых останется только 1 брокер (лидер), Kafka выдаст ошибку `NotEnoughReplicasException` и не
  примет данные, вместо того чтобы записывать их в «небезопасном» режиме.

### Итог по конфигурации «Золотой стандарт»:

Для критически важных данных (финансы, заказы) используй:

1. `acks=all` (на стороне Producer).
2. `enable.idempotence=true` (на стороне Producer).
3. `min.insync.replicas=2` (на стороне Broker/Topic).
4. `replication.factor=3` (на стороне Topic).

## <a id="retries-p">Retries & Timeouts</a>

Когда сеть «мигает» или брокер временно недоступен, Продюсер может сам переотправлять сообщения.

### retries

Этот параметр определяет количество попыток.

* **По умолчанию:** `2147483647` (практически бесконечно).
* **Важно:** В современных версиях Kafka (с 2.1+) рекомендуется **не ограничивать** количество ретраев через `retries`,
  а управлять общим временем попыток.

### delivery.timeout.ms (Самый важный параметр)

Это «верхний предел» времени, за которое сообщение **обязано** дойти до брокера (включая все ретраи и ожидания в
очередях).

* **По умолчанию:** 2 минуты (120000 ms).
* **Как это работает:** Если сообщение не доставлено за это время — продюсер сдается и выбрасывает исключение.
* **Зачем:** Это защищает память приложения от бесконечного накопления старых сообщений, если брокер «умер» надолго.

### retry.backoff.ms

Пауза между попытками переотправки (по умолчанию **100 ms**). Она нужна, чтобы не «спамить» брокер запросами сразу после
сбоя, давая ему время восстановиться.

### Итог по «бесконечным» ретраям:

Для обеспечения гарантии доставки (At-least-once):

1. Оставь `retries` в дефолтном значении (максимум).
2. Настрой `delivery.timeout.ms` под свои требования (например, 30 секунд или 5 минут).
3. Используй `enable.idempotence=true` (обязательно!), чтобы при ретраях не наплодить дублей на брокере.

## <a id="delivery-guarantees-p">Гарантии доставки</a>

В Kafka есть три основных режима обработки сообщений на стороне получателя:

1. **At-most-once (Максимум один раз):** Консьюмер прочитал сообщение, сразу закоммитил офсет, а потом начал обработку.
   Если сервис упадет в процессе — сообщение потеряно навсегда.
2. **At-least-once (Минимум один раз):** Консьюмер прочитал, полностью обработал (записал в БД) и только в самом конце
   отправил подтверждение. Если сервис упадет до коммита — после рестарта он прочитает это сообщение снова. **Это
   стандарт для большинства систем.**
3. **Exactly-once (Ровно один раз):** Реализуется через транзакции Kafka (сложно и медленно).

## <a id="manual-ack-p">Ручное подтверждение (Manual Ack)</a>

Чтобы гарантировать обработку без потерь, нужно отключить автоматический коммит офсетов (enable.auto.commit: false) и
подтверждать их вручную.

### Настройка в Spring Boot (application.yml):

spring:
kafka:
consumer:
enable-auto-commit: false
listener:
ack-mode: manual_immediate

### Пример в коде:

@KafkaListener(topics = "orders", groupId = "my-group")
public void listen(ConsumerRecord record, Acknowledgment ack) {
try {
// 1. Бизнес-логика
orderService.process(record.value());

        // 2. Только если всё прошло успешно — сдвигаем офсет
        ack.acknowledge(); 
    } catch (Exception e) {
        // Если упала ошибка — НЕ вызываем ack.acknowledge().
        // Сообщение вернется в обработку после ребаланса или таймаута.
        log.error("Ошибка обработки", e);
    }

}

## <a id="dlt-p">Dead Letter Topic (DLT)</a>

Если сообщение «битое» (кривой формат), обычный ретрай не поможет — консьюмер зациклится и остановит всю очередь (
Head-of-line blocking). Решение — отправить его в «корзину» (DLT).

### Настройка через @RetryableTopic:

Достаточно добавить аннотацию над слушателем:

@RetryableTopic(
attempts = "3",
backoff = @Backoff(delay = 2000, multiplier = 2.0)
)
@KafkaListener(topics = "orders")
public void listen(String message) {
orderService.process(message);
}

### Как это работает:

1. Если метод кидает Exception, Spring сделает 3 попытки с растущей паузой.
2. Если все попытки провалены, сообщение автоматически улетит в топик orders-dlt.
3. Основной поток консьюмера пойдет дальше, не блокируя остальные сообщения.

## <a id="ordering-p">Порядок данных в Kafka</a>

Зачем в Kafka помещать Key (ID заказа)? В Kafka это самое важное правило для порядка данных.

```java
ProducerRecord<String, String> record = new ProducerRecord<>(
        "order-events", //топик
        event.getAggregateId(), //ключ для партиции, если нулл то по кругу в разные партиции
        event.getPayload().asString()); // значение
```

* **Как это работает:** Если ты шлешь сообщение без ключа, Kafka раскидывает их по партициям (разделам) как попало (
  Round-robin).
* **Проблема:** Если у тебя 3 партиции, то сообщение «Заказ создан» может попасть в партицию №1, а сообщение «Заказ
  оплачен» — в партицию №3. Если сервис-потребитель (Consumer) читает партицию №3 быстрее, он попытается оплатить заказ,
  который еще «не создался».
* **Решение:** Если у сообщений одинаковый Key (ID заказа), Kafka гарантирует, что они всегда попадут в одну и ту же
  партицию. Это значит, что они будут прочитаны строго по очереди.

1. Почему Кафка не считает это дубликатом?
   Настройка ENABLE_IDEMPOTENCE_CONFIG защищает от технических дублей (ошибки сети, повторы самого драйвера).
   Как это работает: Когда сервис отправляет сообщение, Кафка дает ему номер (например, 1). Если из-за лага сервис отправит то же самое сообщение №1 еще раз — Кафка его отбросит.

2. Зачем тогда нужна Идемпотентность?
   Она нужна для ситуаций, когда:
   Продюсер отправил данные.
   Кафка их записала.
   Сеть упала до того, как Продюсер получил ответ "ОК".
   Продюсер сам (автоматически) шлет те же байты еще раз.
   Вот такие дубли Кафка отсекает по внутреннему номеру (Sequence Number). Твои ручные сбросы в БД — это новые команды на отправку.
3. Как с этим жить? (Главное правило)

   Если Шедулер отправил в Кафку, но упал до того, как пометил в базе true — он отправит снова.

1. Паттерн Transactional Outbox
   Проблема: В микросервисах нельзя одновременно сохранить данные в БД и отправить сообщение в Кафку одной транзакцией. Если база сохранится, а Кафка упадет — данные рассинхронизируются.
   Решение: Мы создали таблицу outbox_events. Заказ и событие сохраняются в одну БД одной транзакцией.
   Сложность: В реактивном стеке (R2DBC) мы использовали EntityTemplate.insert(), чтобы избежать лишних проверок (Select-перед-Insert) и гарантировать запись.
2. Гарантии доставки: At-Least-Once
   Теория: Кафка гарантирует, что сообщение дойдет минимум один раз. Но из-за сбоев сети оно может прийти дважды.
   Реализация:
   Producer (Заказы): Почтальон (Scheduler) шлет сообщение и ждет подтверждения. Если подтверждения нет — он шлет снова.
   Consumer (Корзина): Должен быть идемпотентным. Если сообщение о чистке корзины пришло второй раз, сервис просто видит, что удалять уже нечего, и не падает с ошибкой.
3. Идемпотентность Продюсера
   Проблема: При повторных попытках отправки (Retries) в Кафке могут появиться дубликаты.
   Как решили:
   ENABLE_IDEMPOTENCE_CONFIG = true.
   Кафка сама присваивает порядковый номер сообщениям. Если она видит два сообщения с одним номером — второе просто игнорирует.
   В обычной Кафке: Нужно было следить за max.in.flight.requests.per.connection (не более 5).
   В реактивной Кафке: Мы использовали SenderRecord с Correlation ID (наш UUID из базы), чтобы связать ответ Кафки с конкретной записью в Outbox.
4. Backpressure (Обратное давление)
   Проблема: Если в Кафке миллион сообщений, Consumer может «захлебнуться», пытаясь выкачать их все в память.
   Сравнение:
   Простая Кафка: Ты сам пишешь while(true) и poll(Duration). Если обработка долгая, тебе нужно вручную ставить паузу (Thread.sleep) или уменьшать размер пачки.
   Реактивная Кафка: Использует метод limitRate(N). Поток сам говорит Кафке: «Пришли мне 10 штук. Пока я их не обработаю и не подтвержу (acknowledge), новые не шли». Это защищает память сервиса автоматически.

Топ-10 вопросов по Kafka для собеседования:
Что такое ISR (In-Sync Replicas)?
Ответ: Это список реплик (копий), которые полностью синхронизированы с лидером. Если лидер упадет, новым лидером может стать только кто-то из ISR. Настройка acks=all ждет подтверждения именно от всех ISR.
Зачем нужен Consumer Group ID?
Ответ: Чтобы масштабировать чтение. Kafka распределяет партиции топика между участниками одной группы. Один участник — одна партиция (в идеале). Если запустить сервис с новым group-id, он прочитает всё заново.
Как Kafka хранит данные?
Ответ: На диске в виде логов (append-only log). Это делает её невероятно быстрой, так как запись идет последовательно, а не в случайные места диска.
Что такое Partition Rebalancing?
Ответ: Процесс перераспределения партиций между консьюмерами, когда один из них отключается или добавляется новый. В этот момент обработка может ненадолго замереть (Stop the world).
В чем разница между commitSync и commitAsync?
Ответ: Sync блокирует поток до ответа Кафки (надежно, но медленно). Async шлет запрос и идет дальше (быстро, но сложнее обрабатывать ошибки). В реактивной Кафке мы используем acknowledge(), который работает асинхронно и эффективно.
Что такое "Zookeeper-less Kafka" (KRaft)?
Ответ: Новый режим (с версии 3.x), где Kafka сама управляет своими метаданными без Zookeeper. Это упрощает архитектуру и ускоряет восстановление после сбоев.
Как обеспечить гарантию "Exactly Once" (ровно один раз)?
Ответ: Использовать транзакционный продюсер (Transactional Producer) и идемпотентность. Это гарантирует, что сообщение либо будет записано один раз, либо не записано вовсе, даже при ретраях.
Что такое Lag (лаг) консьюмера?
Ответ: Разница между последним сообщением в Кафке и последним прочитанным сообщением сервиса. Большой лаг — признак того, что сервис не справляется с нагрузкой.
Зачем нужны Headers в сообщении Kafka?
Ответ: Для передачи метаданных (например, формат данных, токены авторизации или traceId для логирования), не меняя основное тело (Payload) сообщения.
Что такое Log Compaction?
Ответ: Политика хранения, при которой Кафка удаляет старые сообщения с тем же ключом, оставляя только самое последнее состояние. Полезно для хранения справочников или настроек.

Атомарная проверка (setIfAbsent): Мы используем Redis как "замок". Если два одинаковых сообщения придут одновременно, Redis позволит создать ключ только для одного из них.

Важный нюанс:
Этот подход называется At-Least-Once + Idempotency. Даже если сервис упадет между шагом 2 (очистка корзины) и шагом 3 (подтверждение в Кафку), при повторном чтении Redis скажет: "Я уже видел этот ID", и корзина не будет очищаться повторно.

1. Точка генерации (Клиент vs База)
   Sequence: ID рождается внутри базы в момент выполнения INSERT. Если база получила данные, но «моргнула» и не ответила твоему приложению (таймаут), ты не знаешь, создалась запись или нет.
   UUID: Ты создал его в Java-коде (UUID.randomUUID()). Теперь этот ID — часть твоего объекта еще до похода в базу. Если база выдала таймаут, ты можешь повторить попытку (retry) с тем же самым ID.
2. Сценарий «Сбой при сохранении в Outbox» (Почему Sequence может создать две записи)
   Представь, что у тебя стоит автоматический ретрай на уровне метода create (или пользователь дважды нажал кнопку из-за лага):
   С Sequence:
   Попытка №1: Данные ушли в базу. База сохранила заказ, выдала Sequence 101, но из-за лага сети твой сервис получил TimeoutException.
   Попытка №2 (Retry): Сервис думает, что ничего не вышло, и шлет данные снова. База создает вторую строку (так как это новый запрос) и дает ей Sequence 102.
   Итог: В Кафку улетят два сообщения с разными ID (101 и 102). Консьюмер подумает, что это два разных действия.
   С UUID:
   Если ты сгенерируешь UUID до начала всей цепочки (или передашь его с фронтенда как idempotency-key), то в обеих попытках ретрая ты будешь пытаться вставить запись с одним и тем же UUID.
   База на второй попытке просто выдаст ошибку Unique Constraint Violation (так как такой ID уже есть).
   Итог: Ты никогда не получишь две разные записи в Outbox для одного логического действия.

1. Почему Outbox «несовершенен»?
   В мире нет способа сделать одну транзакцию, которая охватит и базу, и Кафку одновременно (точнее, есть 2PC транзакции, но они настолько медленные и хрупкие, что их никто не использует).
   Поэтому мы всегда делим процесс на две части:
   Запись в базу (Бизнес-логика + Outbox).
   Отправка из Outbox в Кафку.
   Проблема: Между этими шагами всегда может произойти сбой. И если он произойдет, система выберет «лучше отправить дважды, чем не отправить совсем».
2. Справился ли он со своей задачей?
   Справился! Его главная задача — не потерять сообщение, если заказ создался.
   Без Outbox: Заказ создался, Кафка упала -> сообщение исчезло навсегда. (Это потеря данных).
   С Outbox: Заказ создался, Кафка упала -> сообщение лежит в базе и будет отправлено через минуту шедулером. (Это надежность).
3. Кто должен «допилить» это несовершенство?
   Так как Outbox гарантирует, что сообщение дойдет минимум один раз, на сцене появляется Консьюмер.
   Именно поэтому мы обсуждали UUID.
   Outbox гарантирует: «Я по-любому донесу это сообщение до Кафки».
   UUID гарантирует: «Если Outbox из-за сбоя принесет мне это сообщение трижды, я обработаю его только один раз».
   Итог
   Это не «косяк» паттерна, это архитектурный компромисс. Мы меняем идеальную атомарность на гарантированную доставку.
   В распределенных системах мы принимаем как факт: дубли будут всегда. И бороться с ними нужно не на этапе отправки (это невозможно на 100%), а на этапе получения.
   Теперь пазл сложился? Outbox спасает от потерь, а UUID спасает от дублей. Вместе они создают иллюзию идеальной работы.

*   **Transactional Outbox**: Для гарантированной доставки сообщений в Kafka используется паттерн Outbox. Событие для Kafka сохраняется в ту же БД, что и заказ. Если база упала — событие не создастся. Если заказ создался — событие гарантированно будет отправлено позже - `At-least-once` . Но могут быть дубли (при повторной попытке (Retry), если транзакция пройдет, но сервис из за обрыва и таймаута не получит ответ) и тут должен помочь UUID сгенерированный до начала транзакции)
*   **Децентрализованный UUID в Outbox**: Использование UUID вместо БД-сиквенса дает два ключевых преимущества:
   1. **Производительность**: ID генерируется в памяти процессора (наносекунды) без обращения к базе за следующим значением. Это убирает лишнее ожидание ответа от БД в реактивной цепочке.
   2. **Уникальность при интеграции**: UUID гарантирует, что события из разных систем (или даже разных инстансов одной системы) никогда не пересекутся по ID. Это критически важно при объединении данных в общем логе или аналитике, где сиквенсы из разных баз неизбежно начали бы конфликтовать.
   *   *Перспектива*: Текущая архитектура готова к выносу генерации UUID до начала транзакции для реализации полной идемпотентности на стороне базы в будущем.

* **Идемпотентность на стороне базы**: Вынос генерации UUID в `order-Service` до начала транзакции для реализации полной идемпотентности на стороне базы(невозможность повторно создать два события с одинаковым UUID).
* **Идемпотентный потребитель (Idempotent Consumer)**: Внедрение проверки UUID сообщения на стороне получателей (например, в `cart-service`). Использование Redis или таблицы в БД для хранения ID обработанных событий позволит игнорировать повторные сообщения. Переотправки в режиме `At-least-once` неизбежны, если в момент отправки подтверждения (Ack) от Кафки или от БД Шедулеру происходит сбой сети. В этом случае Шедулер отправит сообщение повторно, так как не получил гарантии успешной доставки, хотя сообщение на самом деле могло уже попасть в топик.

1. Как различать «битый JSON» и «сервер упал»?
   Да, это критично. В OrderEventListener (в блоке onErrorResume) нам нужно понять: стоит ли подтверждать офсет (acknowledge).
   Битый JSON (DecodingException / JacksonException): Ошибка в коде или данных. Ретраи не помогут. Подтверждаем, чтобы пропустить это «ядовитое» сообщение, иначе оно заблокирует очередь.
   Ошибки связи (ServiceException / Timeout): Сервис временно лежит. НЕ подтверждаем. Кафка (точнее, библиотека reactor-kafka) сама переподключится, и через некоторое время сообщение придет снова.
   java
   .onErrorResume(ex -> {
   if (isCriticalDataError(ex)) {
   log.error("Битые данные в сообщении, пропускаем: {}", ex.getMessage());
   record.receiverOffset().acknowledge(); // Пропускаем
   } else {
   log.error("Временная ошибка сервиса, попробуем позже: {}", ex.getMessage());
   // НЕ подтверждаем. Кафка перепоставит сообщение.
   }
   return Mono.empty();
   })

2. Про isCriticalDataError
   Это не встроенный метод, это твоя логика проверки типа ошибки. Чтобы понять, «битый» ли это JSON или просто «сервис прилёг», тебе нужно посмотреть на класс исключения:
   java
   private boolean isCriticalDataError(Throwable ex) {
   // Если ошибка десериализации (Jackson не смог прочесть JSON)
   // или ошибка валидации данных — это критическая ошибка данных.
   return ex instanceof com.fasterxml.jackson.core.JsonProcessingException ||
   ex instanceof DecodingException;
   }

4. Ретраи в Кафке (Как это работает на самом деле)
   Кафка сама по себе не делает ретраи для Consumer.
   Если ты не подтвердил офсет (acknowledge) и твой сервис упал или поток закрылся, Кафка просто считает, что сообщение не прочитано.
   Когда ты запустишь сервис снова, он начнет с того же места.
   Твой OrderEventListener должен выглядеть так:
   Попробовал прочитать JSON. Если битый — залогировал и подтвердил (чтобы не застрять на нём).
   Попробовал вызвать сервис. Если сервис выдал 500 — сработал твой retryWhen.
   Если после всех ретраев всё равно 500 — ты не подтверждаешь офсет. Сообщение остается в Кафке «на потом».
