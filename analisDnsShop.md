## Out of scope для DNS-Shop (первая итерация)

### Общее описание

DNS-Shop — это интернет-магазин с типичным для e-commerce функционалом:

*Пользовательская часть:*

* Просмотр каталога товаров (с фильтрацией по характеристикам)
* Регистрация и авторизация
* Добавление товаров в корзину
* Оформление заказов
* Просмотр истории заказов
* Редактирование профиля

*Административная часть:*

* Управление категориями товаров (создание иерархии)
* Управление свойствами товаров (EAV-модель)
* Добавление/редактирование товаров
* Управление справочниками (string_classifier)

*Ключевые особенности проекта (из кода и описания):*

| Особенность | Описание |
| :--- | :--- |
| **EAV-модель** | Товары имеют динамические характеристики (через таблицы property, product_property, string_classifier) |
| **Сложная фильтрация** | Реляционное деление + Criteria API + кастомный CPredicate |
| **Иерархические категории** | Дерево категорий произвольной вложенности (parent_id) |
| **Конкурентный доступ** | PESSIMISTIC_WRITE + @Version + сортировка ID для защиты от дедлоков |
| **Кэширование** | Hibernate 2nd level cache (Ehcache) для категорий и запросов |
| **Гибридный доступ** | JPA для CRUD, JDBC для аналитики (PropertyReadDtoExtractor) |
| **Безопасность** | Spring Security, роли USER/ADMIN, кастомный AuthenticationSuccessHandler |
| **Тестирование** | Testcontainers, JaCoCo (60% покрытие) |
| **Миграции** | Liquibase |

*Сущности БД:*
1. users — пользователи
2. category — категории (дерево)
3. producer — производители
4. product — товары
5. property — свойства товаров (EAV)
6. string_classifier — справочники для свойств
7. product_property — значения свойств для конкретных товаров
8. basket — корзины пользователей
9. basket_product — товары в корзине
10. orders — заказы
11. order_product — товары в заказе

### 1. Административная панель (оставляем в монолите)

**Почему:**

* Низкая нагрузка (админов мало)
* Меньше рисков — если админка временно упадет, пользователи не пострадают
* Сложная логика (EAV, управление свойствами) — проще оставить как есть на первом этапе

**Что именно:** CRUD категорий, товаров, характеристик.

### 2. История заказов (старые данные остаются в монолите)
  
**Почему:**

* Миграция миллионов заказов — сложная и рискованная
* Новые заказы пойдут в новый сервис, старые — читаем из монолита
* Можно реализовать паттерн "Strangler Fig" — постепенное замещение

**Что именно:** Старые заказы (до даты X) — остаются в БД монолита. Просмотр истории показывает заказы из двух источников (монолит + новый сервис)

* Не критично для бизнеса (можно отключить временно)
* Требует отдельного решения (возможно, Elasticsearch позже)

**Почему:**

* В распределенной системе нужен распределенный кэш (Redis), а не Ehcache
* На первом этапе можно обойтись без кэша или с упрощенным решением

### 5. Интеграции с внешними системами

**Почему:** В текущем проекте их нет. Если появятся позже, будут новым микросервисом.

### 6. Тестовая инфраструктура

**Что именно:** Testcontainers, JaCoCo - остаются в монолите. Для новых микросервисов будем писать тесты заново (с учетом их архитектуры)

## Вы затронули фундаментальные различия между реляционным (PostgreSQL) и документоориентированным (MongoDB) подходами.
Давайте разберем ваши пункты более детально, чтобы подтвердить их правильность и добавить немного технического контекста.
1. Дублирование данных и нормализация
   Ваше утверждение верно: PostgreSQL принуждает к нормализации, а MongoDB часто провоцирует денормализацию.
   PostgreSQL: Вы создаете таблицу countries и таблицу products. В товаре хранится только country_id. Это экономит место и, что важнее, исключает аномалии обновления (если название страны изменится, вы меняете его в одном месте).
   MongoDB: Чтобы запрос «все товары для Германии» был мгновенным, разработчики часто встраивают данные. Если вы храните список товаров внутри документа страны, вы столкнетесь с проблемой ограничения размера документа (16 МБ). Если товаров тысячи, они просто не влезут в один объект «Германия».
2. Транзакции и атомарность
   Здесь есть важный нюанс. MongoDB ввела поддержку многодокументных транзакций (с версии 4.0), но PostgreSQL справляется с ними эффективнее «из коробки».
   Сброс кеша и отправка событий: Строго говоря, база данных сама не сбрасывает внешний кеш (например, Redis) и не отправляет события в очередь (RabbitMQ) в рамках своей транзакции. Однако в Postgres есть Transactional Outbox Pattern и логическая репликация, которые позволяют гарантировать, что событие будет отправлено только если транзакция в базе прошла успешно.
   Сложные связи: В Postgres гораздо проще гарантировать, что если вы создали «Заказ», то «Остатки на складе» уменьшились атомарно.
3. Целостность и типы данных
   Это сильнейшая сторона PostgreSQL.
   Деньги: Использовать Int (хранение в копейках/центах) — отличная практика. В Postgres также есть тип NUMERIC, который идеально подходит для финансов, так как исключает ошибки округления, свойственные числам с плавающей точкой (float).
   Constraints (Ограничения):
   CHECK (price > 0) — база просто не примет некорректные данные.
   FOREIGN KEY — гарантирует, что вы не привяжете товар к несуществующей стране.
   Схема: В MongoDB схема гибкая (Schema-less). Это удобно на старте, но через год разработки в одной коллекции могут лежать документы с разными именами полей, что превращает поддержку кода в кошмар.
   Сравнение в таблице
   Критерий	PostgreSQL	MongoDB
   Структура	Строгая (Schema-on-write)	Гибкая (Schema-on-read)
   Связи	Мощные JOIN, Foreign Keys	$lookup (медленнее и сложнее)
   Целостность	Гарантирована на уровне БД	Ложится на плечи разработчика
   Масштабирование	Вертикальное (сложнее горизонтально)	Горизонтальное (шардинг из коробки)
   Резюме
   Ваши аргументы абсолютно верны для систем, где:
   Данные имеют четкую структуру.
   Важна финансовая точность.
   Связи между объектами сложные (много ко многим, иерархии).
   MongoDB лучше выбирать, когда у вас огромные потоки неструктурированных данных (например, логи, сенсоры) или когда формат данных меняется каждый день и вам некогда описывать миграции.

"Я изучил возможность перехода на JSONB. Основные плюсы — упрощение фильтрации и меньше JOIN.
Но в моем проекте есть критичные требования, которые JSONB не закрывает:
Справочники (STRING_CLASSIFIER) с предопределенными значениями
Необходимость массового обновления свойств (например, переименование)
Ссылочная целостность между товарами и свойствами
Строгая типизация значений (числа отдельно, строки отдельно)
EAV с реляционным делением — проверенное решение для таких задач. JSONB я бы рассматривал,
если бы свойства были уникальны для каждого товара и не переиспользовались.
В текущей модели EAV остается оптимальным выбором."

Если бы я перешел на JSONB, код стал бы проще для фильтрации и чтения — убрал бы Criteria API, CPredicate, все JOIN.
Но появились бы сложности с массовыми операциями: переименование свойства,
добавление нового свойства всем товарам, удаление — всё это требовало бы обхода всех товаров и массовых UPDATE.
Также потерял бы ссылочную целостность и строгую типизацию.
EAV дает гибкость администрирования (легко менять свойства) ценой сложности фильтрации. 
JSONB дает простоту фильтрации ценой сложности администрирования.
Для моего проекта, где админка активна (добавление/изменение свойств), EAV подходит лучше.
